# SQL guard feasibility evidence

This is an isolated, inactive schema. It is not a production migration and does not grant application or submission permission. No original table, employer, provider, credential store, hosted account, or installed extension is used by these tests.

The shared async adapter owns each transaction. A new claim atomically records an immutable raw identity, SQL-derived keys, a permanent protection, and events. Submission-kind fixtures also record an intent. Only the first acknowledged commit returns `fresh:true`; every replay or reconciliation returns `fresh:false`. A lost commit response throws `UncertainCommitError` and is never automatically retried. Every result still says `submission_allowed:false`: the complete native authorization checks have not been integrated here.

The database derives identity keys with a pinned Unicode map and recursive SQL, without connection-local JavaScript functions. Indexed keys are independently checked against their raw source on insertion. Direct updates, deletion, replacement, upserts, and forged normalized keys are rejected, including when recursive triggers are disabled. Unknown protected identities block all new claims in their account rather than disappearing from a projection.

Receipt insertion requires the durable attempt, matching account/owner, strict URL attribution, and valid chronology. Receipt plus submitted event are atomic. Replays retain the first receipt and timestamp; later interview, rejection, or offer outcomes remain. Receipt reconciliation never releases the original protection or permits another claim. Both the repository and SQL inspect the full evidence text, without truncating later contradictions. Supported evidence is valid UTF-8 text without NUL, bounded to 8,192 bytes. SQL implements the native English receipt predicate and placeholder veto without a connection-local function. Retained query parameters are checked independently of the broader handoff identity rules, including `lever-source`, `lever-origin` and duplicate-key order.

The isolated preparation repository now exports append-only, revisioned snapshots and requires the latest snapshot, a nonfuture age of at most five minutes, and a matching current protection digest before reservation or replay. It checks owner, applicant, identity, account Stop and account-wide holds in the transaction that creates the claim and reservation metadata. Projection reads are paged and bounded; malformed or incomplete protections fail closed. Missing or pending imports now block export and claims; only a completed verified import can produce a snapshot. Its output identifies the isolated model; `submission_allowed:false` always remains. Completed imports identify their source snapshot and limited projection scope.

Generic preparation claims and reconciliation require that same lifecycle. SQL binds raw preparation writes to immutable snapshot checks and a current append-only state epoch. It rechecks server-clock age, latest revision, identity, owner, applicant, Stop and holds. The repository authenticates the projection SHA-256; SQL independently enforces the current epoch and live protections even against fabricated matching digests. SQL bounds projected size conservatively at 512 plus six times source bytes per row, intentionally rejecting some otherwise valid native projections.

Latest integration and mandatory import checkpoint: [ASYNC-PREPARATION-CHECKPOINT.md](../ASYNC-PREPARATION-CHECKPOINT.md). Its 199 passing tests supersede the historical count below.

## Earlier executed checks

Run `npm run test:async`. Its parent process owns temporary SQLite files and deletes them only after the libSQL test process exits.

The latest integrated suite has **183 passing tests, zero failures and zero skips**: 32 prior async database/API tests and 151 guard/import tests. Coverage includes independent clients competing for one identity; preparation versus submission races; process restart; direct SQL writes; Stop; account isolation; rollback of partial intent/receipt graphs; and committed-but-lost responses through the official HTTP driver with a replaced, synthetic transport. These are not live Turso measurements. See `../guard-history-import-tests.log`.

Receipt text tests compare 5,387 distinct bounded cases on both native SQLite and local libSQL (10,774 differential comparisons), including full-length contradictions, placeholders, Unicode whitespace and invalid UTF-8. Receipt query tests compare 225 pairs per driver (450 comparisons). Thirty-two preparation lifecycle tests cover snapshot revision, age and digest, replay after Stop/holds, conflicting request ownership, independent-client races, lost commit responses, immutable metadata, raw writer bypasses and oversized or incomplete projections. An earlier full `npm test` run passed 635 native tests, four UI checks and the then-current 88 async tests. The newer native receipt fix and its separate regression results are recorded in `../GUARD-IMPLEMENTATION.md`.

Identity qualification compares 1,112,063 Unicode scalars, 2,039 complete normalization examples, 103 annotation variants, and 144 duplicate pairs against native oracles on native SQLite and local libSQL. The original scan-based lookup took about 2.3 seconds at 10,000 identities. The indexed implementation measured 0.135 ms for one identity and 85.6 ms for all keys in the integrated run; query planning confirms a primary-key lookup. The 10,000-row insert took 5.77 seconds locally, so remote imports must use bounded batches while a durable import hold prevents claims.

## Protected-history import

The trusted offline importer has 32 passing tests and verifies one pinned source transaction against a complete snapshot manifest. It preserves immutable evidence and outcomes in bounded batches. A durable pending-import hold blocks claims, replay, reconciliation and preparation exports until independently verified completion. Empty imports invalidate earlier snapshots too. Ordinary DML cannot forge completion or append evidence after completion. No claims, submission intents or receipts are fabricated from imported history. See [HISTORY-IMPORT.md](HISTORY-IMPORT.md) for the inventory, failure behavior and deployment boundary.

## Remaining integration gates

- The URL parser supports a strict subset of native WHATWG URL behavior. Percent escapes, nontracking query parameters and other unsupported forms fail closed. Candidate fixtures are Greenhouse, Lever and Ashby; this is not full native platform parity.
- Supported receipt-path aliases and broader URL behavior remain unported. Native `receipt-sync.js` has a separate full-text fix in this isolated checkout, with 25 passing targeted tests recorded in `../native-receipt-fulltext-tests.log`; the original checkout and production path remain unchanged and require coordinated deployment.
- The mandatory AP2 snapshot fence covers this isolated guard schema, including generic `claimCandidate(kind='preparation')` and raw preparation claim writers. Native production callers remain unconnected. The offline protected-history importer is integrated only with this inactive schema. SQL uses the current epoch and live protection checks; cryptographic digest recomputation remains repository-owned.
- The full focus/campaign/consent/profile/eligibility policy remains unintegrated. Permanent holds here also do not implement native quota expiry/release semantics.
- The protected-history projection covers 15 reviewed native sources; full application-state migration, all native raw job-transition fences, executable quarantine signature handling, remaining connection-local functions and synchronous callers are still incomplete. A source backup must retain every native row/table and resume; this prototype is not that backup.
- Runtime writers are trusted to use the installed schema. An administrator who disables foreign keys or drops triggers/DDL is outside this proof. Runtime schema administration must not be exposed through the application API.

See [native-invariants.md](native-invariants.md) for the distinction between existing native guarantees and additional direct-write hardening.
