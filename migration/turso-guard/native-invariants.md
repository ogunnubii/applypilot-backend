# Native guard invariants for the remote SQL port

Read-only source/test audit at local commit `2ce8369c43e137806f4c21e73c7cbbdc97688d31`. This document maps existing behavior; it is not a claim that the remote implementation or a production migration passes these checks. No tests were executed for this audit and no production data was read.

## Identity oracles must remain distinct

- `application-dedup.js:19` `sameApplication(a,b)`: same ATS requisition OR equal nonempty `applicationRoleKey` plus intersecting employer aliases. Employer aliases include `companyKey(company)` and supported ATS path tenant. Its protection is **user-wide**, not merely per applicant. Protected old statuses are submitted/interview/rejected/offer/archived/queued/running/local_browser, or any non-null local attempt. Different ATS requisitions can still match by role/employer, intentionally conservative.
- `application-history.js:2-3` `historyKey`/`companyKey`: NFKD accent folding and alphanumeric compaction, legal suffix removal for company, fixed aliases (Clutch Technologies, ARHS Developments, PricewaterhouseCoopers). External history uses `historyKey(title)`, not the display-annotation-stripping role key. Unique history is `(user_id, company_key, title_key)` independent of outcome. Re-importing plain applied cannot erase a later outcome.
- `preparation-handoff.js:13-46` `handoffURL`, `handoffIdentity`, internal `matches`: canonical public HTTPS URL, ATS/tenant/requisition, or role + employer alias intersection. Candidate ATS metadata is derived and validated, not trusted caller metadata. Supplied alias arrays do not get to enlarge the derived alias set. Location does not distinguish an application. URL-less external history remains protective. Invalid protected URLs abort the entire export, rather than omitting rows. Projection size limits similarly fail closed.
- `employer-limits.js:4` `employerKey`: ATS tenant before company fallback. Do not reduce all Greenhouse/Lever/Ashby jobs to one platform-wide hold. `companyApplicationKeys` additionally handles SmartRecruiters, Workable, BambooHR, Recruitee and Workday aliases for activity.
- Receipt attribution is a different `sameApplication`: `local-policy.js` re-exports `extension/policy.js:30-41`. It requires supported HTTPS URLs and strict normalized URL identity, with employer-specific Greenhouse/Workday/custom-site canonicalization and only recognized trailing form/receipt paths and tracking parameters removed. Do not use fuzzy employer/role matching to attribute a receipt.

## Durable protection and release rules

`company_application_activity` has no job foreign-key cascade. Queueing reserves the exact normalized URL; starting/attempting/outcomes make `started_at` permanent using COALESCE. Only activity with `started_at IS NULL` is deleted on untouched unqueue or job deletion. Startup seeds started work before untouched reservations, preserving existing outcomes while marking untouched exact aliases duplicate.

AP2 journal protection ordering is excluded > uncertain > reserved. Any non-saved row is protected; independent attempt events also retain protection. Protection records contain only identity/status, not answers, notes, receipt text, or applicant details. Export additionally includes orphaned activity, URL-less external history, reservations, and employer holds. A later hold can block rechecking an already accepted reservation. AP2 reservation replies always set `submission_allowed:false`.

`unresolvedAttemptEligibility` accepts only stopped recognized states: applicant-reported submitted, or needs_review + unconfirmed + no local owner for hosted. It requires handoff exactly zero, verifying/uncertain phase, local attempt, and the appropriate event. Hosted requires a hosted-worker reservation and latest lifecycle event needs_review. No dispatching continuation is allowed. Parking writes the marker/event and pauses only the owner's focus in one transaction, without changing the job evidence. An idempotent parking retry must not clear a newer different focus.

## Claim authorization is more than a unique row

`reserveAutonomousAttempt` rechecks current focus/batch/campaign authorization, consent/email/resume, supported form, posting availability, eligibility/search scope, French exclusion, actual employer holds, drafting consent, repeat/external history/AP2 checks, owner and execution mode, and manual-review restrictions within the reservation transaction. Cover letters/preparation campaigns never grant automatic submission. It rejects existing submission evidence even if a job status was changed back. Saved-search mode additionally enforces the selected profile, current search signature, fresh posting check, strong match, no other in-flight job, and untouched candidate requirements.

One-job authorization stops after that named job; receipt/removal does not authorize the next. Best-effort selection moves only past pre-submit blockers. A preparation count is not a submission: the narrowly allowed takeover path requires an explicit queue request newer than the last worker claim and no attempt evidence (`single-application.js:112-123`). Porting must not confuse that exception with automatic retry.

## Receipt transaction oracle

Local receipt requires account + browser owner + non-null local attempt + strict same application URL + `afterSubmit === true` + affirmative receipt text. Hosted receipt requires account + no local owner + existing hosted-worker reservation + strict same application URL + affirmative receipt. Both validate before returning alreadySynced, so a receipt does not become a cross-owner information leak.

Local eligible states are local_browser/submitted/interview/rejected/offer; hosted also supports running/needs_review. Observed time is accepted only between the durable attempt and now; otherwise now is used. The receipt stores the original application URL, attributed receipt URL, attempt, owner, receipt text, and timestamps. Local receipt ID is bounded to 80 characters. Duplicate calls preserve those first values. Event insertion checks both submitted and manual_confirmation. Hosted running/needs_review/submitted may become submitted; local only local_browser or applicant-reported submitted becomes submitted. Later interview/rejected/offer stay unchanged.

`extension/policy.js` receipt parser rejects explicit failure/negation/pending/possible-spam text, including contradictory adjacent sentences. `operation-evidence.js` also excludes placeholders/simulations/unconfirmed/quota-refusal text and requires a recorded receipt event. An application-limit message is never receipt evidence.

## Actual employer hold details

Security rejection inserts a durable hold and at most one rejection event without changing any job's status, challenge, receipt, ownership, or attempt. Security takes precedence over quota; a later quota report cannot relabel it. SQL fences block automatic queue/running transitions; higher-level claim/preparation checks also call `employerHold`.

Quota notice alone does not imply limit reached. Explicit refusal is authoritative even with missing off-platform history. Repeated reports preserve the first active report/hold instead of extending it. Known distinct employer receipts count by recorded receipt time, not later interview/rejection update time; URL aliases collapse. Attempts/queued rows/placeholders/other applicants do not count as confirmed slots. An uncertain attempt count does not imply success or authorize retry. The inferred rolling window and explicit conservative reported hold are combined; unknown-duration refusal remains indefinite.

## Native limits that must not be misrepresented as proven SQL guarantees

The inspected native system assumes trusted mutators for auxiliary guard tables. It has no delete/update-denial triggers protecting direct writes to `autonomous_attempts`, `employer_receipts`, `company_application_activity`, AP2 reservation/protection tables, or quarantine markers. Guarding those raw operations remotely is additional hardening and needs explicit tests.

Repeat/history triggers mainly watch status and NULL-to-non-NULL attempt changes. Repeat INSERT marking is only for new saved rows; history INSERT marking is broader. Neither is a universal company/title edit fence. Company activity locks started URL/normalized URL, not all display identity fields. AP2 identity-update fence and journal are stronger. Therefore a remote proof must include raw identity edits and raw guard-table mutations or clearly enforce a restricted writer boundary; do not infer universal native coverage from happy-path repository tests. Also test SQL `REPLACE`/upsert behavior when introducing immutable-table protections.
